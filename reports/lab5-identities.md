# Scoped identities and permission exercise

| Identity | Scope and permissions | Why |
|---|---|---|
| lab5-training | Reader on the ML workspace; Blob Data Contributor only on the workspace artifact container; AcrPull only on the registry | Read the deployed incumbent, read input data, persist training outputs, and pull the runtime image. No model registration or endpoint write role. |
| lab5-serving | Blob Data Reader on the artifact container and a conditional reader on only Lab 5 startup manifests in azureml (no listing through that grant); AcrPull on registry; Monitoring Metrics Publisher on existing App Insights | Read the registered model and image and publish telemetry. Cannot overwrite training data or register/deploy models. |
| lab5-ci | AzureML Data Scientist on the workspace; Blob Data Contributor on artifact container; AcrPush on registry; Managed Identity Operator on the serving identity only | Submit jobs, register candidate artifacts, deploy staging, push images, and attach the serving identity. It cannot assign arbitrary RBAC roles or modify shared compute through the ML Data Scientist role. |

The developer's interactive identity performs the initial bootstrap of identities, narrowly scoped role assignments and compute. It is not the runtime training or serving identity. No account key is copied into the job or image.

The registry and artifact container are existing shared lab resources; scope is at that container/registry rather than subscription. A dedicated per-lab container would reduce training write scope further, at the cost of configuring a separate ML datastore and grants. The broad workspace ML Data Scientist role is constrained to the existing workspace; a production system should split its staging deployment permissions into a custom role and separate workspace.

Actual principal IDs and role assignments are recorded in reports/evidence/identity-assignments.json. The actual managed permission probe `sharp_tiger_8v16syprpk` returned HTTP 403 / AuthorizationFailed when the training identity tried to list staging endpoints after its workspace Reader grant was removed. The scoped blob permissions remained in place. This disproved the assumption that artifact access alone was sufficient: incumbent discovery also needs control-plane read access. The Reader grant was restored in the finally block; `permission-exercise.json` records restoration, and `permission-denied.txt` retains the actual managed stdout. No broad role was added.

The restored Reader grant initially still returned 403 in managed jobs. After the cluster was observed scaling to zero and a fresh node was prepared, managed probe `funny_cake_2b2kbzz208` completed with allowed=true using the same training identity and the same restored Reader scope. See permission-restoration-check.json and permission-restored.txt. No broader role was added. This records recovery as well as configuration restoration; Azure propagation/cache delay was an operational issue.

Isolation limit: the demonstration cluster has both the training and CI user-assigned identities attached, while each command job explicitly selects its intended client ID. The scoped grants demonstrate principal-level permissions; this is not evidence of host isolation against hostile training code. A production promotion runner should use separate compute or federation so untrusted training code cannot potentially request a promotion identity available on the same host. The current lab uses trusted course code and one user-owned cluster.

The deployment initializer required its own model manifest in the separate `azureml` container. Following explicit user approval, a temporary conditional Blob Data Reader assignment permits reads only of `itcs355-lab5-staging_blue_model_config_map.json_*` and excludes Blob.List. The original model-artifact container grant remains. No account-wide reader was granted. The exact condition and assignment ID are retained in serving-manifest-reader.json and the teardown journal.

Recovery proof: the retry initializer completed image pull, model download and user-container startup successfully. The targeted zero-traffic invocation returned model version 188317299 and probability 0.008443148980236426. See manifest-retry-initializer.json and deployment-preflight.json. This proves the manifest-only grant was sufficient for this startup; final teardown removes it.

Final cleanup removed all recorded Lab 5 role assignments and identities. An independent GET for the manifest-only assignment returned RoleAssignmentNotFound; see cleanup-protection-proof.json. The role table above documents the exercise permissions, not currently active access.
